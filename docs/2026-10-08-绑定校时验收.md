# 绑定时间与时区同步验收

验证日期：2026-10-08。测试手机：OnePlus MT2110；测试锁盒：S8534_c6d9f2；海外 Debug 包。

## 原问题与修复

- TTLock 正常绑定没有显式提交时间戳和时区；MHT 初始化发送校时后未等待回执，提前报告初始化成功。
- 密码生成使用手机当前时区，手机出行换时区后可能与锁的有效时间不一致。
- 现在先保存初始化凭据和绑定时区，写锁时间并读回核验，再上传服务器并通过 `lock/get` 回查保存的时区。全部通过后才完成绑定；失败保留记录并支持重试，不重复初始化物理锁。
- 限时、循环密码请求使用保存的锁时区；自定义密码时间转换和相关 MHT 协议格式化也使用锁的偏移。
- 实测发现 TTLock SDK 3.5.6 的 `connectLock` 已连接分支回调成功后仍占用命令槽，导致紧接的校时失败。连接成功后释放该回调，再发送校时指令。

## 三端实测

所有时间均按 Asia/Shanghai（UTC+8）记载；时间戳单位为毫秒。

| 对象 | 证据 | 结果 |
| --- | --- | --- |
| 手机 | 时区 `Asia/Shanghai`，偏移 `28800000`；校时发送值 `1791436475076`（13:14:35.076） | 通过 |
| 锁 | SDK 回读 `1791436475417`（13:14:35.417），`lock verified=true`，偏移 `28800000` | 补偿通信耗时后的误差在 5 秒容差内 |
| 服务器 | 13:14:40.950，`lock/get` 回查偏移匹配 `28800000`；13:14:41.207 空间绑定成功 | 通过 |
| 失败重试 | 首次校时失败明确提示、保留未同步设备；更新包后点击“同步”，使用原凭据完成校时、上传和空间绑定 | 通过，未重新初始化锁 |

云端初始化参数含 `timestamp=1791436149530`（13:09:09.530）和 `timezoneRawOffSet=28800000`。该时间戳保留 SDK 初始化基准，避免影响密码算法；重试校时采用新的手机当前时间。服务器验收证据为接口回查的时区，不代表已直接查询服务器数据库或服务器系统时钟。

## 补充：先切换手机时区，再首次配对并立即创建密码

产品重点场景是首次配对后设置的密码是否可用。此前“绑定后切换手机时区”的测试不能替代本场景，因此单独重测。

1. 使用 App 正常删除 c6d9f2，完成物理锁重置及账号移除，删除接口返回 `code=200, success=true`；重启 App 后首页无设备。
2. 配对前将手机切到 `America/Los_Angeles`，系统属性确认，当前偏移为 UTC-7（`-25200000`）。
3. 从添加设备入口重新配对这把已恢复未绑定状态的锁；绑定全程未手动校时，也未进入未同步设备补传流程。
4. 绑定完成后直接进入密码管理，列表只有新管理员密码；立即生成第一条限时密码并在实体锁键盘输入。
5. 再生成一条每日循环密码，补充验证本次绑定保存的时区。

以下日志为洛杉矶当地时间 2026-10-07；对应北京时间 2026-10-08，小时加 15。

| 步骤 | 实测证据 | 结果 |
| --- | --- | --- |
| 初始化后自动校时 | 22:27:38.911，手机发送 `1791437258911`，偏移 `-25200000` | 手机采集通过 |
| 锁回读 | 22:27:39.274，`readTimestamp=1791437258257`、`verified=true`，偏移 `-25200000` | 校时误差在 5 秒容差内 |

| 每日循环密码 | 22:30:34.971，`keyboardPwdType=6`、`timeZone=-7`，每天 22:00–23:00 | 失败；用户重复输入两三次，锁均提示“开锁失败” |

首条密码在自动校时及服务器校验完成后约 58 秒发起生成，期间未手动校准时间。结论：UTC-7 首次配对、三端校时及首条限时密码通过，但同次绑定的循环密码失败，整体验收尚未完成。此次没有运行旧版本作对照，也不代表所有型号均通过。

后续回查发现，失败循环密码的服务端记录为 `startDate=1791522000000,endDate=1791525600000`，对应锁当地 **10 月 8 日** 22:00–23:00；生成时当地是 **10 月 7 日** 22:30，生效被推迟一天。应有值为 `1791435600000,1791439200000`，与已成功的限时密码记录一致。

用户提供的下载目录静态后端代码包含对应缺陷：控制器使用服务器默认时区选择当天及星期，再按请求时区解析，能够精确复现实测错误。已制作[后端补丁及部署验收说明](backend-cycle-timezone/README.md)，独立 Java 8 时间换算回归通过 59 个断言，补丁在快照副本上的应用检查通过。原静态快照未修改，远端未部署，不能将其表述为循环密码已修复或已实测通过。

手机已恢复 `Asia/Shanghai` 并核实；测试锁保留本轮绑定的 UTC-7。另发现删除设备后返回旧“添加成功”页的问题，原因是成功页跳转详情后未退出；已补充 `finish()`，重新构建安装后继续完成上述配对测试。未再次删除设备专门回归该返回路径。

## 补充：设备详情页时区提示

按用户确认的范围，Android 详情页新增非阻断提示：手机与锁的已保存时区不同时，显示“当前手机与锁的时区不同，密码有效时间以锁的时区（UTC±HH:mm）为准”。时区相同或服务器未提供有效时区时隐藏；重新进入页面、收到系统时区变更通知时更新。提供默认英文、简体中文、繁体中文文案。提示不提供同步按钮，也不会改写锁的时区。

首次绑定继续使用本文已实测的自动同步流程：写入手机当前时间及绑定时区，读回校验锁时间，上传并回查服务器时区，通过后才进入绑定成功页；失败保留重试入口。

新增提示后海外 Debug 构建及 `git diff --check` 通过，测试包已成功覆盖安装。用户重新登录后完成提示的真机验收：c6d9f2 当前详情返回的锁时区为 UTC-10:00，手机为 Asia/Shanghai，顶部提示完整显示且未遮挡操作按钮；临时把手机切到 Pacific/Honolulu（UTC-10）后提示自动隐藏，恢复 Asia/Shanghai 后提示自动重新显示。截图与 UI 层级均检查通过。手机已恢复原时区，本次未重复绑定、改写锁时区或操作实体锁；此处 UTC-10 为本轮读取到的当前设备数据，不替换前述 UTC-7 首次绑定历史实测记录。

## 实体锁验证范围

本次实体锁验收覆盖 TTLock S8534_c6d9f2 的 UTC+8 绑定、失败重试、UTC-7 首次配对路径，以及上述有效时段内的密码开锁。MHT 实体锁、其余绑定时区、跨夏令时自动调整，以及密码到期边界尚未完成实体锁测试。MHT 现有协议只能表示部分整小时时区，无法表示的偏移会明确拒绝，避免静默截断。当前实现保存并使用绑定时的固定偏移，不承诺自动随夏令时变化。
