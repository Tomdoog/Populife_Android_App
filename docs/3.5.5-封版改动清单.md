## 二、重构

### 设备删除一致性：三态受控删除链路（`4f2768c` + 未提交增强）

按产品《设备删除一致性与异常恢复》重构，**不新增后端接口**。原来蓝牙物理删除和账号删除各走各的，中途被杀进程/断连就留下"锁已重置但账号里还挂着"或反过来的幽灵设备。

**主链路**：删除准备 `lock/user/check` → 蓝牙物理删除 → 账号移除 `lock/del/v2`

**三态留痕**（`helper/DeviceDeleteState.java`）：物理删除指令发出**前**先写状态，防 App 被杀丢失上下文
| 状态 | 含义 | 处理 |
|---|---|---|
| `DELETING` | 指令已发、结果未回 | — |
| `PENDING_ACCOUNT`（状态A） | 物理删除已确认成功 | 详情页弹窗引导完成账号移除 |
| `UNKNOWN`（状态B） | 超时/断连，结果未知 | 详情页弹窗要求用户实测确认后再移除 |

- 30s 扫描超时兜底；**结果未知态明确禁止重试物理删除**（需求文档 八.3）
- 详情页恢复弹窗 `helper/DeviceDeleteRecoveryDialog.java`
- 移除原 `pending_server_delete` 临时补丁

**未提交部分的三处增强：**

1. **状态B 的 Remove 前置判定**（需求 七.B）
   账号移除不可逆——记录一删，lockData 和管理员权限跟着没，App 再也发不出蓝牙删除指令，锁会变成谁也管不了的孤儿。所以状态B 点 Remove 先弹判定："到设备旁试初始密码，能开吗？" 能开（=已回出厂态）才允许移除；开不了/连不上则保留记录、不移除，提示靠近重试或联系客服。新增 5 条 7 语言文案。

2. **覆盖添加同一把锁时静默收尾**（`DeviceDeleteRecoveryDialog.onSameLockReAdded`）
   用户不走"完成移除"、直接重置后重新添加同一把锁，是最常见的自救路径。`DeviceDeleteState` 增加 **MAC → lockId 索引**：
   - 服务端复用 lockId → 旧记录直接作废（否则刚添加成功的设备一进详情页就被判成"待账号移除"，点 Remove 等于把新设备删掉）
   - 服务端换发新 lockId → 旧 id 是云端幽灵记录，补发 `lock/del/v2` 静默清掉，不弹窗、不再验密码（刚完成添加，所有权已证明）
   - 清理失败不清本地记录，详情页弹窗仍能兜底
   接入点：`FoundDeviceActivity`（2 处）、`OfflineLockListActivity`（2 处）、`OfflineLockUploader.completeSync`

3. **状态A 不再屏蔽详情页操作入口**
   弹窗只做引导——用户点 Later 后仍要能查旧密码、看开锁记录，入口一律照常展示（`LockDetailFragment`）
