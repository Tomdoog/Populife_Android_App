# K4 Android 记录同步与补传

本次修复客户端已确认的失败处理缺陷，尚未通过客户现场接口日志确认“8 月后记录断档”的根因。版本号保持 3.5.6（356），未发布。

## 行为

- App 开闭锁事件、K4 SDK 读取的原始记录批次，在发请求前写入私有 SQLite 数据库 `lock_record_outbox.db`。
- 四个 SDK 记录上传入口统一使用队列；查询和上传使用当前钥匙的设备 ID。
- HTTP 成功且业务 `code=200` 才删除待传记录。网络失败、HTTP 错误、业务拒绝、异常响应均保留。
- 首次失败等待 30 秒，然后指数退避至最长 30 分钟；失败记录不阻塞其他到期记录。
- 网络恢复、进入首页、App 回到前台触发检查。进程存活时定时重试；进程被系统关闭后，下次打开 App 恢复，不承诺关闭后后台运行。
- 按原账号、服务器隔离，保留原设备 ID、钥匙 ID 和记录内容。退出账号不删除待传记录，登录其他账号不会补传原账号的数据。
- 上传未成功但已落盘时提示“已保存、将自动补传”；落盘失败则提示重新同步，不虚报已保存。
- 本次覆盖 K4 的科技侠 SDK 记录及 App 操作上报，不改变 `pplock` 内部的负 ID 设备批量记录协议。

## 已接受的限制

用户明确要求先采用“至少一次”投递：服务端入库但响应丢失、确认后本地删除失败等情况可能重复，服务端去重后续处理。本地串行队列只防止同一条待传记录并发发送，不能实现服务端去重。

App 事件的原始时间 `createdAt` 和本地 UUID 保存在队列中。当前 `operation/log/add` 请求仍只有原有参数，尚未向服务端传入它不支持的发生时间或幂等 ID；后台如何给补传 App 事件标记时间需服务端确认。SDK 批次保留原始记录及其中的时间字段。

## 验证

- 18 项 JVM 测试通过：响应校验 6 项、队列 12 项，覆盖断网、进程重建、账号/环境隔离、并发触发、失败退避、磁盘写入失败、传输异常及迟到回调。
- API 33 模拟器 3 项测试通过：设备 ID 一致性 2 项、SQLite 持久化 1 项。数据库测试使用独立临时数据库，模拟器断网运行，不向生产上传测试记录。
- 国内和海外 Debug Java 编译通过，国内 Debug APK 与测试 APK 构建通过；未执行实体锁或生产后台入库验收。

后续内部真机验收：断网 App 开锁后联网，检查补传入库；读取 K4 指纹/密码/NFC 记录后模拟上传失败，重启 App 验证补传；核对设备删除重绑前后的 `lockId` 与后台查询环境。
