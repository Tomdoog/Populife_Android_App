# Populife Android App 功能模块梳理（重构评估用）

> 版本 3.5.4 · 343 个 Java 文件 · 98 个 Activity + 16 个 Fragment · 纯 Java、无正式架构
> 梳理日期：2026-07-22

## 一、产品全貌：这个 App 是做什么的

智能门锁 App，围绕「锁」展开的四大能力：

1. **锁的接入与控制**（蓝牙开锁、添加设备、固件升级、网关远程）
2. **钥匙/凭证分发**（电子钥匙、密码、指纹、IC 卡的发放与管理）
3. **售后服务**（维修工单、保修、PopuCare 付费服务）
4. **账号与内容**（登录注册、家庭管理、使用手册/视频/商城）

关键背景事实：**项目同时接了两套锁 SDK、两条产品线**：

| 产品线 | SDK | 对应包 | 状态 |
|---|---|---|---|
| 老锁（Deadbolt、KeyBox 等） | TTLock（通通锁）`com.ttlock:ttlock:3.5.6` | `lock/`（28 个回调接口） | 在用（存量设备） |
| 新锁（Manhattan Moon Lock，`PPL_ML`） | 自研 pplock 模块 `com.populock.manhattan.sdk` | `manhattanlock/`（28 个回调接口） | 在用（主力，App 启动初始化的是它） |

业务代码里到处是 `if (锁名以 PPL_ML 开头) { 走自研 SDK } else { 走 TTLock }` 的双分支，两套回调接口几乎逐字重复——**这是重构最大的抽象/去重收益点**。

## 二、导航结构与页面清单

- 启动流程：`SplashActivity`（唯一 launcher，含 `share://` 深链）→ 未登录 `SignActivity` / 已登录 `MainActivity`
- 主界面：RadioGroup + ViewPager 硬编码 3 个底部 Tab（无 Navigation Component）：

| Tab | Fragment | 内容 |
|---|---|---|
| 智能（Lock） | `MainLockFragment` | 锁详情 + 锁列表（ViewPager 套 ViewPager），加锁、家庭、说明书入口 |
| 发现（General） | `MainGeneralFragment` | 使用手册 / 操作视频 / 商城（新闻子页已注释屏蔽） |
| 我的（Me） | `MainMeFragment` | 个人中心、设置、消息、网关、离线锁、服务支持、注销 |

Manifest 注册 95 个 Activity，其中 **8 个已无任何有效跳转（死页面）**，详见第四节。

## 三、模块清单：在用 / 弃用状态

### 在用（核心）

| 模块 | 功能 | 备注 |
|---|---|---|
| `lock/` | TTLock SDK 蓝牙操作回调接口层（老锁线） | ~24 个页面引用 |
| `manhattanlock/` | 自研 pplock SDK 回调接口层（新锁线） | 52 个文件引用，当前主力 |
| `activity/`（76 文件） | 全部页面：锁管理、密码/钥匙收发、IC 卡指纹、网关、家庭、消息、帮助 | 无架构分层，业务全在 Activity 里 |
| `keypwdmanage/` | 密码/蓝牙钥匙/指纹/IC 卡管理页 | 双 SDK 分支重灾区 |
| `home/` | 家庭管理 + `HomeDeviceInfo` 设备型号判定中枢 | 全局锁分支都依赖它 |
| `me/`、`sign/`、`find/` | 个人中心、登录注册处理、发现页内容 | find 的 NewsList 已弃用 |
| `maintservice/`（17 文件） | 维修工单、保修、PopuCare | 付费子流程绑死已弃用的 PayPal |
| `push/` | **自研 Redis 长轮询推送**（异地登录、钥匙状态变更） | 在用但方案高危，见风险 |
| `helper/` + `db/` | 新加的离线锁补传器 OfflineLockUploader + 手写 SQLite（单表） | 2026 新功能，防绑定中断变砖 |
| `net/` | RestClient Builder + 回调风格封装（Retrofit 2.4 + fastjson 手动解析） | Cookie 会话，无 token |

### 弃用 / 半废弃

| 项 | 依据 |
|---|---|
| **pay/paypal 支付** | 环境写死 `ENVIRONMENT_NO_NETWORK`（mock 模式，不产生真实交易）；PayPal 该原生 SDK 官方已 EOL；代码多处「用不上」注释。实质从未上线 |
| **新闻资讯**（`find/NewsListFragment`） | 唯一装载处在 `MainGeneralFragment` 被注释「屏蔽新闻页面」 |
| **MobSDK/ShareSDK 分享** | 初始化整段注释，仅剩死配置 |
| **TTLock 云端绑定路径** | `MyApplication.initLock()` 空实现、绑定逻辑约 50 行整体注释，新增绑定已全走自研 SDK |
| **8 个死 Activity** | `ModifyPinCodeActivity`、`LockGroupSelectActivity`、`LockManageIcCardActivity`、`LockUserListActivity`、`MessageDetailActivity`、`KeyPwdTypeSelectActivity`、`LockManageBluetoothKeyActivity`、`ResetPwdActivity` —— 注册了但跳转入口全被注释或不存在 |
| **5 个死类/备份类** | `MainMeFragment_backup`、`MainGeneralFragment_backup`、`MainMeFragment00`、`MaintServiceActivityback`、`BackupEkeyPermissionModifyActivity` —— 0 引用 |

## 四、技术栈与风险点（讲重构必要性的弹药）

**技术栈现状**：AGP 8.6 / compileSdk 35（构建链不旧），但业务侧是 2018 年的世界——Java 8、无架构（胖 Activity MVC）、无 ViewModel/DI/协程，viewBinding 是唯一的现代化点。

### 安全风险（优先级最高）

1. **客户端直连生产 Redis**：`push/EventPushService` 用 jedis 直连 `v2.server.populife.co`，**Redis 密码明文硬编码在 APK 里**。任何人反编译即可连上生产 Redis。应替换为 FCM/标准推送。
2. **fastjson 1.1.67**：存在多个历史反序列化 RCE 漏洞。
3. **release 不混淆**（`minifyEnabled false`），debug/release 共用同一签名 keystore。
4. 环境切换靠在 `Urls.java` 里改注释，无 buildType/flavor，发版易错。

### 过时依赖（均为 2016–2018 年版本）

OkHttp 3.11 / Retrofit 2.4 / Glide 3.7（已被 4.x 完全取代）/ appcompat & material 1.0.0 / EventBus 3.0 / PayPal SDK（已死）/ Bugly 用 `latest.release` 动态版本（构建不可复现，且 Bugly 已入停服周期）/ fastjson 与 Gson 两套并存 / libphonenumber 两份并存。

### God Class（拆分重点）

| 类 | 行数 | 问题 |
|---|---|---|
| `LockDetailFragment` | 2209 | 锁详情：双 SDK + 网络 + 推送 + UI 全塞一个类 |
| `LockSettingsActivity` | 1545 | 锁设置 |
| `PasscodeDetailActivity` | 1512 | 密码详情 |
| `KeyPwdListFragment` | 1501 | 凭证列表 |
| `SignActivity` | 1341 | 登录/注册/验证码一屏全包 |
| `BaseActivity` | 756 | 公共容器，注册广播、客服入口 |
| `MyApplication` | 702 | 持有两套 SDK 全局句柄，单个匿名回调类 ~480 行 |

另有全局单例耦合：`PeachPreference`（SharedPreferences 封装，88 个文件引用）、`RestClient`（76 文件）。

## 五、给领导讲的重构方案建议（按收益排序）

1. **止血（低成本、可先做）**：删除死页面/死类/弃用模块（8 Activity + 5 备份类 + NewsList + ShareSDK 残留）；下线 PayPal 链路（本来就没真实交易）；开启混淆。
2. **安全整改（必须做）**：推送从「客户端直连 Redis」迁到 FCM；升级 fastjson 或统一到一套 JSON 库；环境配置改用 buildType/flavor。
3. **核心抽象（重构主体）**：把 `lock/` 与 `manhattanlock/` 两套平行接口收敛为统一的锁能力抽象层（一个 `LockRepository` 接口 + 两个 SDK 适配器），消灭遍布全局的 `if manhattan / else ttlock` 双分支——这是后续接第三条产品线的前提。
4. **架构升级（随抽象逐步做）**：按页面逐个迁移到 MVVM（ViewModel + Repository），优先拆 2000+ 行的 `LockDetailFragment`；依赖整体升级（OkHttp4/Retrofit2.x 新版/Glide4 或 Coil）。
5. **不建议动的**：`helper/OfflineLockUploader` + `db/` 是刚上的新功能，方案虽简单但自洽，重构时保留语义平移即可。
